## Application State

**Application state** is all the data your app needs to remember while it runs: what the user typed, what they favorited, which screen they're on. You can divide it into two kinds:

- **Local state** — matters to one component (a text field's contents)
- **Shared state** — matters to many components (the user's favorites, the theme)

The art of state management is choosing the *right place* for each piece of data: keep it local when you can, lift it up when others need it.

## Component Communication

Data flows in React in one direction — **down**, from parent to child, via props. When a child needs to tell a parent something, the parent passes down a *callback function* as a prop:

```jsx
function App() {
  const [favorites, setFavorites] = useState([]);

  return (
    <RouteList
      favorites={favorites}
      onToggle={(id) => setFavorites(/* add or remove id */)}
    />
  );
}
```

- Data (**favorites**) flows **down** into `RouteList`
- Actions (**onToggle**) flow **up** from `RouteList` to `App`

Mastering this one pattern — data down, callbacks up — solves most communication problems. When "prop drilling" (threading props through many layers) gets painful, that's when you reach for the [Context API](context-api/).

## Data Modeling

Before you write state logic, decide what your data **looks like**. Good data models make the rest easy.

Think in **shapes**. A route and its favorites:

```js
// Route object
{ id: 12, name: 'Farmington Ave', direction: 'To Downtown', stops: [...] }

// Favorites — a set of route ids
[12, 27, 45]
```

Ask three questions:

1. **What is a single item?** — define its fields
2. **What collections exist?** — routes, stops, favorites
3. **What changes?** — which fields does the user edit (favorites) vs. which stay fixed

Model data *before* building screens. Screens built on a clear model are far easier to build and far harder to break.
