## REST APIs & JSON

An **API** (Application Programming Interface) is how your app asks another system for data. **REST** is the most common style, and **JSON** is the data format.

Your app sends a request to a URL, and the server responds with JSON data:

```js
[
  { "id": 12, "name": "Farmington Ave", "arrival": "5:42 PM" },
  { "id": 27, "name": "Asylum Ave", "arrival": "6:05 PM" }
]
```

See [REST APIs & JSON](rest-apis-and-json/) for the details.

## Loading and Error States

Network requests are **slow** (hundreds of milliseconds at best) and **unreliable** (offline, servers down, data changed). Your UI must handle three states for every request:

| State | What the user sees |
|---|---|
| **Loading** | A spinner or skeleton while waiting |
| **Success** | The data, rendered |
| **Error** | A clear message + a retry action |

A well-designed loading/error experience is often the difference between an app that feels broken and one that feels professional. Users should never be left staring at a blank screen wondering if the app hung.

## Data Reliability

Public APIs change, go down, and return unexpected data. Protect your app with three habits:

1. **Validate what you get** — don't assume the data shape; guard against missing fields
2. **Handle empty results** — "no results" is a valid, common outcome; show it gracefully
3. **Cache the last good data** — combine with [Week 8's AsyncStorage](../week-08-local-data-persistence/) so your app works offline with the last-fetched data

This is the offline-first thinking from last week, applied to API data.
