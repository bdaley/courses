# Hermes Agent — Courses Website (.hermes.md)

## Project: Courses (Astro + Starlight)

- **Repo:** https://github.com/bdaley/courses
- **Local:** ~/projects/courses
- **Build:** `npm run dev` (localhost:4321) | `npm run build` (→ dist/) | `npm run preview`
- **Deploy:** GitHub Actions → GitHub Pages (auto on push to `main`)
- **Node:** v26 (use `npm run` scripts, not npx directly)

## When the user says "make an update" — workflow

1. **Read** the relevant file(s) with `read_file` / `search_files` first — never edit blind.
2. **Edit** using `patch` for small changes or delegate to OpenCode/Claude Code for larger tasks:
   - **Small fixes** (typo, single page, content update) → edit directly with `patch` / `write_file`.
   - **Large tasks** (new section, new course, refactor) → use `delegate_task` with OpenCode or Claude Code via `claude -p` / `opencode run`.
3. **Verify** the build compiles: `npm run build` (no lint/test scripts exist in this repo).
4. **Commit** with a clear message on an isolated branch: `git checkout -b feat/<description>`.
5. **Open a PR** if the user wants one — use `gh pr create` with a body linking to any GitHub issue.
6. **Post the PR link** back to the user.

## Astro + Starlight specifics

- Content lives in `src/content/docs/` as `.md` (plain) or `.mdx` (with component imports).
- Pages using `<InteractiveCode>` or `<Quiz>` **must** be `.mdx` — never `.md`.
- Each course is a top-level directory under `src/content/docs/` (e.g., `dmd-1070/`, `dmd-3440/`).
- Add a new course: create its dir + `index.mdx`, then add a sidebar group in `astro.config.mjs`.
- Set `prev: false` on each course's `index.mdx` and `next: false` on each course's final page to stop pagination at boundaries.
- The first sidebar item of each course group should be `{ slug: '<course-dir>' }`.
- `starlight-image-zoom` is already configured — all images get click-to-zoom automatically.
- No lint, typecheck, or test scripts — rely on `npm run build` for verification.

## When a GitHub issue is opened

When the user says "issue #N" or "GitHub issue": follow the **issue-to-PR** workflow:
1. `gh issue view <N> --comments` — read body + all comments for live state.
2. `gh pr list --search "#<N>"` + keyword variants — check for duplicates.
3. Implement the fix on an isolated branch with a regression test (if applicable).
4. Run `npm run build` to verify.
5. Open a PR with `gh pr create --fill` and link the issue.
6. Comment on the issue thread with the PR link.

## Available coding agents

| Agent | When to use |
|-------|-------------|
| **Hermes** (direct) | Content edits, small fixes, file renames, straightforward code changes |
| **OpenCode** | Complex multi-file refactors, new component implementations |
| **Claude Code** | Full architectural changes, large feature implementations |

All agents work in isolated worktrees to avoid git conflicts.

## Conventions

- Commit messages: conventional commits (`feat:`, `fix:`, `docs:`, etc.)
- Branch names: `feat/<short-desc>`, `fix/<short-desc>`, `docs/<short-desc>`
- PR titles: match the issue title or describe the change clearly
- Prefer editing existing files over creating new ones when reasonable
